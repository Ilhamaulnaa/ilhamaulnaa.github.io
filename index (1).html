Draft · Architecture

Why Eventhings uses a multi-module architecture

Eventhings has many flows: authentication, home, media partners, sponsors, rentals, all the way to checkout and payment. With everything in one module, a small change in one flow easily touches another.

So the app is split into several modules. Each screen follows MVVM, and Koin wires dependencies across modules. Module boundaries forced us to think about what one feature is allowed to know about another.

The result is cleaner, more maintainable code, and team members can work on different features without colliding as often.

Draft · Android

Downloads that keep going when the app is minimised

In MEVER, users download videos and photos and usually switch to another app right away. The download has to keep running, and users must be able to pause, resume or cancel it at any time.

Android restricts background work, so downloads need to run through the mechanisms the system provides for it. MEVER uses the Ketch library to manage those downloads.

Download state is observed as a Kotlin Flow. That keeps the pause, resume and cancel buttons on the Compose screen in step with the real state of the download.

Draft · Learning

From XML to Compose, then KMP: notes on learning Kotlin

I learned Android through several routes: Dicoding classes, the Startup Android Jakarta bootcamp, then Bangkit 2023. That is where I picked up Kotlin, Android fundamentals and Jetpack Compose.

Today I use both. At work I maintain older Kotlin code, while Eventhings and MEVER are built with Compose.

What helped most when switching was understanding state and architecture first, and how to draw the interface second. The same MVVM pattern holds in XML and in Compose, and it carries over to Kotlin Multiplatform.
